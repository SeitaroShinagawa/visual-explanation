1. アーキテクチャ詳解

BAGEL の設計を支える 3 つの仕掛け —— 二重の視覚エンコーダ・Mixture-of-Transformer-Experts・ Generalized Causal Attention を、テンソル形状とコードで確認します。

まず全体の骨格

Bagel.__init__ を読むと、このモデルが何を持っているかが 30 行で分かります。 生成用(visual_gen)と理解用(visual_und)が独立したフラグになっていて、 それぞれが自分用の部品を足していく構造です。

modeling/bagel/bagel.py L61–99 GitHub ↗
class Bagel(PreTrainedModel):
    def __init__(self, language_model, vit_model, config: BagelConfig):
        super().__init__(config)
        self.language_model = language_model
        self.hidden_size = config.llm_config.hidden_size
        self.use_moe = "Mo" in config.llm_config.layer_module   # ← MoT を使うかの判定
        self.num_heads = config.llm_config.num_attention_heads

        if config.visual_gen:                                    # ===== 生成側 =====
            self.latent_patch_size = config.latent_patch_size    # 2
            self.timestep_shift = config.timestep_shift
            self.latent_downsample = config.vae_config.downsample * config.latent_patch_size  # 8*2 = 16
            self.max_latent_size = config.max_latent_size        # 64
            self.latent_channel = config.vae_config.z_channels   # 16
            self.patch_latent_dim = self.latent_patch_size ** 2 * self.latent_channel  # 2^2*16 = 64
            self.time_embedder = TimestepEmbedder(self.hidden_size)
            self.vae2llm = nn.Linear(self.patch_latent_dim, self.hidden_size)   # 64  → hidden
            self.llm2vae = nn.Linear(self.hidden_size, self.patch_latent_dim)   # hidden → 64
            self.latent_pos_embed = PositionEmbedding(self.max_latent_size, self.hidden_size)

        if config.visual_und:                                    # ===== 理解側 =====
            self.vit_model = vit_model
            self.vit_patch_size = config.vit_config.patch_size          # 14
            self.vit_max_num_patch_per_side = config.vit_max_num_patch_per_side  # 70
            self.vit_hidden_size = config.vit_config.hidden_size
            self.connector = MLPconnector(self.vit_hidden_size, self.hidden_size, config.connector_act)
            self.vit_pos_embed = PositionEmbedding(self.vit_max_num_patch_per_side, self.hidden_size)
        ...

    def _init_weights(self):
        if self.config.visual_gen:
            nn.init.constant_(self.llm2vae.weight, 0)   # ← 出力ヘッドをゼロ初期化
            nn.init.constant_(self.llm2vae.bias, 0)
ここで読み取れること LLM と外界をつなぐ部品はたった 3 つの線形層です: vae2llm(潜在→LLM)・llm2vae(LLM→潜在)・connector(ViT→LLM)。 NExT-GPT や CoDi-2 の「射影 MLP」と同じ役回りに見えますが、決定的に違う点があります —— その先に別のモデルが待っていない。llm2vae の出力は拡散モデルへの条件ではなく、 拡散過程そのものの予測値(速度場)です。

そして llm2vae はゼロ初期化されています。 学習開始時、モデルが予測する速度場は恒等的に 0 —— つまり 「何もしない」状態から学習が始まります。 DiT 系でおなじみの、残差ブランチをゼロから立ち上げる作法がここでも使われています。

1. 二重の視覚エンコーダ — 同じ画像を 2 回符号化する

BAGEL は 1 枚の画像を2 つの経路で別々にトークン化します。

解像度と語数の対応

2 つの経路は数字がきれいに噛み合うように設計されています。

ViT 経路VAE 経路
前処理(app.py) ImageTransform(980, 224, 14) ImageTransform(1024, 512, 16)
1 トークンが担う画素 14 × 14(patch_size) 16 × 16(VAE の 8× 圧縮 × 2×2 パッチ)
最大の辺 980 px → 980/14 = 70 パッチ 1024 px → 1024/16 = 64 パッチ
設定値の上限 vit_max_num_patch_per_side = 70 max_latent_size = 64
1024×1024 画像のトークン数 (980×980 に縮小して)70×70 = 4900 64×64 = 4096

つまり vit_max_num_patch_per_side も max_latent_size も、 「その解像度で許される 1 辺あたりのパッチ数」そのものです。 どちらも PositionEmbedding の 2D sin-cos テーブルの 1 辺として使われます (PositionEmbedding(64, hidden) なら 64²=4096 行のテーブル)。

⚠️ 微妙だが重要な点: 画像は「1 つの RoPE 位置」しか占めない シーケンス上の位置符号(RoPE 用の packed_position_ids)は、 画像 1 枚につき 1 個しか進みません。4096 個の潜在トークン全部が同じ位置 IDを共有します。
data/dataset_base.py L454(vae_image 分岐の末尾) GitHub ↗
sequence_status['packed_position_ids'].extend([curr_rope_id] * (num_img_tokens + 2))
画像内部の位置関係は RoPE ではなく、足し算される 2D sin-cos 埋め込み (latent_pos_embed / vit_pos_embed)が担当します。 役割分担は「RoPE = 文脈の中で何番目の要素か」「2D sin-cos = その画像の中のどこか」。 おかげで 4096 トークンの画像を挟んでもテキスト側の位置は 1 しか進まず、 long-context の消費が抑えられます。

2. MoT — 同じ attention、違う重み

BAGEL の心臓部が Qwen2MoTDecoderLayer です。 定義を見ると、Transformer 層の構成要素がきれいに 2 セットずつ並んでいます。

class PackedAttentionMoT(Qwen2Attention):
    def __init__(self, config, layer_idx: Optional[int] = None):
        super().__init__(config, layer_idx)
        if self.config.qk_norm:
            self.q_norm = Qwen2RMSNorm(self.head_dim, eps=config.rms_norm_eps)
            self.k_norm = Qwen2RMSNorm(self.head_dim, eps=config.rms_norm_eps)
            self.q_norm_moe_gen = Qwen2RMSNorm(self.head_dim, eps=config.rms_norm_eps)
            self.k_norm_moe_gen = Qwen2RMSNorm(self.head_dim, eps=config.rms_norm_eps)
        ...
        self.q_proj_moe_gen = nn.Linear(self.hidden_size, self.num_heads * self.head_dim, bias=True)
        self.k_proj_moe_gen = nn.Linear(self.hidden_size, self.num_key_value_heads * self.head_dim, bias=True)
        self.v_proj_moe_gen = nn.Linear(self.hidden_size, self.num_key_value_heads * self.head_dim, bias=True)
        self.o_proj_moe_gen = nn.Linear(self.num_heads * self.head_dim, self.hidden_size, bias=False)

q/k/v/o の射影も、QK-Norm も、FFN も、LayerNorm も、すべて 2 セット。 つまり Transformer の重みは丸ごと 2 倍あります。これが 「7B activated / 14B total」の正体です —— 7B のモデルを 2 つ抱えているが、1 つのトークンが通るのは片方だけ。

では、何が共有されているのか

共有されるのはattention の計算そのもの、すなわち 「誰が誰を見るか」の場だけです。forward_train を見ると、 q/k/v をトークンごとに別の重みで作ってから、1 つのテンソルに書き戻しているのが分かります。

        packed_query_states = packed_sequence.new_zeros((packed_sequence.shape[0], self.num_heads * self.head_dim))
        ...
        packed_sequence_und = packed_sequence[packed_und_token_indexes]   # テキスト + ViT トークン

        packed_query_states[packed_und_token_indexes] = self.q_proj(packed_sequence_und)

このあと flex_attention が混ざった q/k/v をまとめて 1 回計算します。 テキストトークンの query が VAE トークンの key を見ることも、その逆も、 何の障壁もなく起こります。出力側でまた o_proj / o_proj_moe_gen に振り分けられます。

MoE との違い 一般的な MoE は「FFN だけを複数用意し、ルータが確率的に選ぶ」方式です。BAGEL の MoT は ①FFN だけでなく attention の射影も LayerNorm も分ける、 ②選択はルータではなくトークンの種別で決定的に決まるという 2 点で異なります。 論文は 1.5B 規模で Dense / MoE / MoT を比較し、 理解と生成の両立という観点で MoT を採用したと報告しています。 「生成タスクが理解タスクの重みを壊す(干渉)」問題を、 容量を分けることで正面から回避する設計です。

3. Generalized Causal Attention — 1 枚のマスクに 3 つの規則

統一モデルにとって最大の技術的難所は、 「まだ生成していない画像」を列の中に置きながら、答えを覗かせないことです。 BAGEL はこれを attn_modes という 3 値のラベルで解決します。

モード付く対象ブロック内部他から見えるか
'causal'テキスト下三角(通常の因果)見える
'full'ViT トークン / ノイズなしの VAE トークン全結合(双方向)見える
'noise'生成対象の(ノイズ入り)VAE トークン全結合(双方向)見えない

そしてどのブロックも、自分より前のブロックはすべて見られます ('noise' ブロックを除いて)。これが「一般化された因果性」の意味です。

data/data_utils.py L13–40 — FlexAttention 版の実装 GitHub ↗
def create_sparse_mask(document_lens, split_lens, attn_modes, device):
    def causal_mask(b, h, q_idx, kv_idx):
        return q_idx >= kv_idx                       # ふつうの因果マスク

    def full_and_noise_mask(b, h, q_idx, kv_idx):    # 同じ full/noise ブロック内は双方向
        return (full_and_noise_seq_id[q_idx] == full_and_noise_seq_id[kv_idx]) & (full_and_noise_seq_id[q_idx] >= 0)

    def remove_noise_mask(b, h, q_idx, kv_idx):      # noise ブロックは「外」から見えない
        return (~((noise_seq_id[kv_idx] >= 0) & (noise_seq_id[q_idx] != noise_seq_id[kv_idx])))

    def sample_mask(b, h, q_idx, kv_idx):            # パックされた別サンプルへは越境しない
        return document_id[q_idx] == document_id[kv_idx]
    ...
    return and_masks(or_masks(causal_mask, full_and_noise_mask), remove_noise_mask, sample_mask)

最後の 1 行がすべてを語っています。 「(因果 または 同一ブロック内双方向)かつ ノイズ隠し かつ サンプル分離」。 4 つの述語の論理合成としてマスクが定義されており、 FlexAttention がこれを疎なブロックマスクにコンパイルします (論文は素朴な SDPA に対して約 2 倍の高速化と報告しています)。

FlexAttention を使わない場合の実装(prepare_attention_mask_per_sample)を読むと、 同じ規則がもっと直接的に書かれています。

data/data_utils.py L72–103 GitHub ↗
def prepare_attention_mask_per_sample(split_lens, attn_modes, device="cpu"):
    sample_len = sum(split_lens)
    attention_mask = torch.zeros((sample_len, sample_len), dtype=torch.bool, device=device)

    csum = 0
    for s, attn_mode in zip(split_lens, attn_modes):
        assert attn_mode in ['causal', 'full', 'noise']
        if attn_mode == "causal":
            attention_mask[csum:csum + s, csum:csum + s] = torch.ones((s, s), device=device).tril()
        else:                                   # full も noise もブロック内は双方向
            attention_mask[csum:csum + s, csum:csum + s] = torch.ones((s, s))
        attention_mask[csum:csum + s, :csum] = 1       # ← 前のブロックは全部見える
        csum += s

    csum = 0
    for s, attn_mode in zip(split_lens, attn_modes):
        if attn_mode == "noise":
            attention_mask[:, csum : csum + s] = torch.zeros((sample_len, s))   # 列を丸ごと消して
            attention_mask[csum : csum + s, csum : csum + s] = torch.ones((s, s))  # 自分だけ復活
        csum += s
    ...
2 段構えになっているのがポイント 第 1 ループで「ブロック内 + 前方すべて」を組み、 第 2 ループで noise ブロックの列を丸ごと 0 に潰してから、対角ブロックだけ 1 に戻す。 行(誰が見るか)ではなく列(誰から見られるか)を操作するのが肝で、 これにより「自分は文脈を全部読める / 誰も自分を読めない」という非対称な可視性が実現します。

3 つ目の埋め込み: 時刻

VAE トークンの埋め込みは、実は3 つの足し算でできています。

modeling/bagel/bagel.py L194–197 GitHub ↗
packed_timestep_embeds = self.time_embedder(packed_timesteps)      # ノイズ時刻 t
latent_token_pos_emb = self.latent_pos_embed(packed_latent_position_ids)  # 画像内 2D 位置
packed_latent = self.vae2llm(packed_latent) + packed_timestep_embeds + latent_token_pos_emb
packed_sequence[packed_vae_token_indexes] = packed_latent

拡散 Transformer では時刻 \(t\) を AdaLN で全層に注入するのが定石ですが、 BAGEL は入力埋め込みに 1 回足すだけです。 LLM 側のアーキテクチャに一切手を加えず、 「時刻もまた入力の一部」として扱う —— 統一モデルらしい割り切りと言えます。
