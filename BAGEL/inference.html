3. 生成プロセス

同じモデルの中にまったく性質の違う 2 つの生成ループが同居しています —— 1 トークンずつ伸ばす自己回帰と、全パッチを同時に 50 回磨く ODE 積分。 その分岐点と、両者をつなぐ KV キャッシュを追いかけます。

2 つの生成ループ

BAGEL の推論は InterleaveInferencer が統括します。 やっていることは「文脈を KV キャッシュに積み上げていき、最後にどちらかのループを回す」だけです。

文脈の積み上げ方

画像を文脈に入れるとき、VAE と ViT の両方が積まれます(学習時の編集データと同じ形)。

理解タスクでは VAE を積まない interleave_inference は画像を積むとき vae=not understanding_output を渡します。 つまりVQA やキャプションのときは ViT トークンだけ、 編集や参照付き生成のときはViT + VAE の両方。 「画素レベルの情報は、画素を再現する必要があるときだけ積む」という割り切りで、 理解タスクの文脈長を大幅に節約しています。

条件画像を積むときの時刻は timestep=0 です (prepare_vae_images の既定値)。 学習編で見たとおり、時刻 0 = ノイズ混合率 0 = きれいな潜在。 学習時に -inf → sigmoid → 0 で作っていた状態と、推論側で数値が一致します。

テキスト生成 — 素直な自己回帰

生成の起点は <|im_start|> トークン 1 個です。

ここは普通の LLM とまったく同じです。 特筆すべきは mode="und" が固定である点 —— テキストを書いているあいだ、Gen Expert の 7B は一切動きません。 「14B のうち 7B しか活性化しない」という表現は、まさにこのことを指しています。

画像生成 — ODE を 50 回積分する

画像側は、まず純ノイズのトークン列を作るところから始まります。

そして積分ループ本体。わずか 10 行ほどです。

modeling/bagel/bagel.py L691–754(generate_image 抜粋) GitHub ↗
        x_t = packed_init_noises

        timesteps = torch.linspace(1, 0, num_timesteps, device=x_t.device)   # t: 1 → 0
        timesteps = timestep_shift * timesteps / (1 + (timestep_shift - 1) * timesteps)
        dts =  timesteps[:-1] - timesteps[1:]
        timesteps = timesteps[:-1]

        for i, t in tqdm(enumerate(timesteps), total=len(timesteps)):
            timestep = torch.tensor([t] * x_t.shape[0], device=x_t.device)
            if t > cfg_interval[0] and t <= cfg_interval[1]:
                cfg_text_scale_ = cfg_text_scale       # CFG を効かせる区間
                cfg_img_scale_ = cfg_img_scale
            else:
                cfg_text_scale_ = 1.0                  # 区間外は CFG オフ(1 回分の forward で済む)
                cfg_img_scale_ = 1.0
            v_t = self._forward_flow(x_t=x_t, timestep=timestep, ...)

            x_t = x_t - v_t.to(x_t.device) * dts[i]    # velocity pointing from data to noise

        unpacked_latent = x_t.split((packed_seqlens - 2).tolist())           # 前後の特殊トークン 2 個を除く
        return unpacked_latent
式で書くと 学習で当てた速度場は \(v = x_1 - x_0\)(データ→ノイズ向き)でした。 生成はその逆向きに辿るだけです。 $$x_{t-\Delta t} \;=\; x_t \;-\; v_\theta(x_t,\,t,\,c)\cdot \Delta t$$ \(t=1\)(純ノイズ)から \(t=0\)(データ)へ、オイラー法で降りていきます。 拡散モデルの DDIM のように \(\alpha_t,\sigma_t\) の係数を掛ける必要がなく、 引き算 1 つで書けるのが Rectified Flow の実装上の利点です。

timestep_shift(推論の既定 3.0)は時刻の刻み方を歪めます。 $$t' \;=\; \frac{s\,t}{1 + (s-1)\,t}$$ \(s>1\) なら \(t'>t\) となり、ノイズが多い側(構図が決まる序盤)に多くのステップが配分されます。 README の説明「higher values allocate more steps at the start (affects layout)」がこれです。

生成し終えた画像は、文脈の中で「きれいなもの」に差し替えられる

interleaved な生成(画像を出したあと、それを踏まえてさらにテキストや画像を出す)では、 生成中に使っていたノイズ入りトークンをそのまま文脈に残すわけにはいきません。 論文 §2.3 は、この後始末を明示しています。

論文 §2.3 より “During inference, the generalized causal structure allows us to cache key-value (KV) pairs of the generated multimodal context and thus accelerate multimodal decoding. Only the KV pairs of clean VAE tokens and ViT tokens are stored; once an image is fully generated, the corresponding noised VAE tokens in the context are replaced by their clean counterparts.”

学習時に 'noise' モードが「ノイズ入りトークンを他から見えなくする」役割を果たしていたのと、 きれいに対応しています —— ノイズ入りトークンは最初から最後まで文脈に寄与しない。 生成が終わればお役御免で、その位置には確定した潜在(あるいは ViT 特徴)が座り直します。 だから次の生成ステップは、あたかも最初からその画像が入力として与えられていたかのように進みます。

公開コードでこれを担うのが InterleaveInferencer.update_context_image() です。 前述のとおり、生成された画像を次の文脈に入れるときは timestep=0(= ノイズなし)の VAE トークンとして積み直されます。

二重の CFG — 3 つの文脈を並走させる

BAGEL の guidance は 2 種類あります。 テキストへの追従度(cfg_text_scale)と 入力画像の保持度(cfg_img_scale)です。 そのために、異なる文脈を持つ 3 つの KV キャッシュを用意します。

cfg_renorm_typeノルムの取り方正規化のタイミング用途(README より)
global全トークン・全チャネルで 1 つ2 段階の外挿を終えたあとT2I の既定。編集がぼやけるときもこれ
channelトークンごと(チャネル方向)2 段階の外挿を終えたあとトークン単位で抑える
text_channelトークンごとテキスト CFG の直後(画像 CFG の前)編集向き。ただしぼけやすい
⚠️ global はバッチサイズ 1 前提 コード中のコメントが明言しているとおり、torch.norm(v_t) は テンソル全体で 1 つのスカラーを返します。 NaViT 方式で複数枚を 1 本にパックすると、別の画像のノルムまで混ざります。 公開実装が実質バッチ 1 に限定されているのはこのためです。

CFG の効く区間を絞る

cfg_interval(既定 [0.4, 1.0])は ノイズが多い前半だけ CFG を効かせ、後半は素の予測に任せる設定です。 区間外では cfg_*_scale_ = 1.0 になり、 _forward_flow 内の if cfg_text_scale > 1.0 が偽になるので、 追加の forward が丸ごとスキップされます。 50 ステップ中 60% で forward が 3 回 → 1 回に減るので、実行時間も目に見えて縮みます。

think が効く理由 統一モデルだからこそ、この一手が意味を持ちます。 LLM が書いた「計画」はそのまま KV キャッシュに積まれ、 画像生成の 50 ステップすべてで attention の対象になります。 外部拡散モデル方式なら、この計画は結局 CLIP テキスト埋め込みに圧縮し直さなければなりません。 論文が報告する CoT の効果は、この「考えたことがそのまま条件になる」構造で説明できます。

なお生成された思考は gen_context にだけ足され、 cfg_text_context / cfg_img_context には足されません。 つまり思考の内容もまた CFG で強調される条件の一部になります。

おまけ: TaylorSeer による高速化

enable_taylorseer=True にすると、 数ステップに 1 回だけ本物の forward を行い、その間は各層の出力を Taylor 展開で外挿します。 modeling/cache_utils/taylorseer.py の既定は fresh_threshold = 3(3 ステップに 1 回は本計算)、 max_order = 6(6 次までの差分を保持)、 first_enhance = 5(最初の 5 ステップは必ず本計算)。 flow の軌跡が時刻に対してなめらかであることを利用した近似で、 モデルの重みには一切触れません。 CFG を使う場合は3 つの文脈それぞれに別のキャッシュが用意されます (model_pred_cache_dic / ..._text_... / ..._img_...)。

まとめ — 3 モデルを通して見えたこと

本シリーズで読んできた 3 つのモデルは、 「LLM とマルチモーダル生成をどう繋ぐか」という同じ問いに、 異なる時代の異なる答えを出しています。

  • NExT-GPT — 言語の比喩を最後まで保つ。LLM は「注文書」を書き、生成器はそれを読む。 安価に組めるが、注文書の語彙が帯域になる
  • CoDi-2 — 途中で言語を降りる。LLM は連続ベクトルを書き、生成器はそれを条件に取る。 言葉にならない情報も通せるが、1 本のベクトルという細さは残る
  • BAGEL — 繋ぎ目をなくす。生成対象そのものが LLM のトークン列に住み、 全文脈と self-attention で直接やりとりする。帯域制限は消えるが、 生成能力を一から学ぶための桁違いのデータと計算が要る

BAGEL の論文タイトルが “Emerging Properties” であることは示唆的です。 接着方式では「繋ぎ方の設計」が能力の上限を決めていました。 繋ぎ目を無くした BAGEL では、上限を決めるのはデータと規模になり、 その結果として能力が段階的に「生えてくる」—— これはまさに、言語モデルが辿ってきた道筋そのものです。
