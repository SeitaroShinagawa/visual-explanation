CoDi-2 図解

画像・音声・テキストが入り混じった指示を文脈ごと理解し、任意のモダリティで応答する マルチモーダル LLM「CoDi-2」(CVPR 2024)。 テキストは離散トークンで、それ以外は連続ベクトルで「書く」という 独特な生成方式を、実装コードの引用とアニメーション図解で読み解きます。

CoDi-2 とは

CoDi-2 (In-Context, Interleaved, and Interactive Any-to-Any Generation, Tang+, CVPR 2024)は、 UC Berkeley / Microsoft Azure AI / Zoom / UNC Chapel Hill による 対話型のマルチモーダル LLM(MLLM)です。 公式 README の言葉を借りれば、その狙いは

公式 README より “By aligning modalities with language for both encoding and generation, CoDi-2 empowers LLMs to not only understand complex modality-interleaved instructions and in-context examples, but also autoregressively generate grounded and coherent multimodal outputs in the continuous feature space.” (CoDi-2/README.md)

ポイントは “in the continuous feature space” の一語です。 CoDi-2 は画像を作るとき、「画像を表す特別な語彙トークン」を新しく覚えるのではなく、 LLM の隠れ状態そのものを 1024 次元の連続ベクトルに射影して、それを拡散モデルの条件として渡します。 テキストは従来どおり離散トークンの自己回帰生成、テキスト以外は連続ベクトルの自己回帰生成 —— この 2 本立てが CoDi-2 の生成プロセスの核心です。

3 つの登場人物

  • 入力側: ImageBind が画像・音声・テキストを共通の 1024 次元空間へ。ただし後述のとおり画像側は改造されており、1 枚 = 1 ベクトルではなくパッチ列を返します
  • 中核: Llama-2-7b-chat-hf + LoRA(rank 128)。理解も、テキスト生成も、特徴生成もすべてここが担当
  • 出力側: Stable Diffusion 2.1 unCLIP(画像)、AudioLDM2(音声)、zeroscope v2(動画)。 とくに画像側はテキスト条件ではなく画像埋め込み条件(c_adm)で動くので、LLM が吐いた 1024 次元ベクトルをそのまま受け取れます

これらを繋ぐのは codi_llama_proj と codi_llama_decode という たった 2 つの小さな MLPです。巨大モデル本体は凍結され、 学習されるのは LoRA と この 2 つの MLP だけ —— という構図は NExT-GPT とよく似ています。 違いは「LLM と拡散モデルの間で何をやりとりするか」にあります。

論文が定める学習目的(§3.2) 論文はこの「LLM に条件特徴を書かせる」枠組みを、次の 1 本の式にまとめています。 $$\mathcal{L} \;=\; \alpha\,\mathrm{MSE}\big(c_{\text{MLLM}},\, C_x(x)\big) \;+\; \mathcal{L}_{DM} \;+\; \mathcal{L}_t$$ \(c_{\text{MLLM}}\) は LLM が生成した条件特徴、\(C_x(x)\) は生成すべきターゲット \(x\) を条件エンコーダに通したもの、 \(\mathcal{L}_{DM}\) は拡散モデルの標準的な生成損失、\(\mathcal{L}_t\) はテキストトークン予測損失です。

この 3 項が、公開コードの 特徴回帰損失 / 拡散損失 / テキスト CE 損失 にそれぞれ対応します。重み \(\alpha\) はコードでは 0.1 です。 数式とコードの突き合わせは学習編で行います。
論文が明かす、この設計のいちばんの妙(§3.2) なぜ「ターゲット画像そのもの」ではなく「ターゲットをエンコーダに通した特徴」を教師にするのか。 論文はこう書いています —— “we explicitly induce that \(c = C_x(x)\), i.e., MLLM is trained to generate \(C_x(x)\) and DM is expected to function as an autoencoder in this case.”

つまり拡散モデルを「エンコーダ側だけ LLM に肩代わりさせたオートエンコーダ」とみなす、という発想です。 本来 \(C_x(x)\) を作るのはエンコーダの仕事ですが、その出力を LLM に予測させれば、 デコーダ(拡散モデル)は何も変えずに再構成器として使い回せます。 学習ターゲットが明確な連続ベクトルになるため、「より強く直接的な教師信号」が得られる、というのが著者の主張です。

全体アーキテクチャ

データの流れは 「ImageBind でエンコード → 射影して LLM の入力列に差し込む → LLM が推論 → テキストと <p> マーカーを生成 → マーカー直後の隠れ状態を逆射影 → 拡散モデルへ」 です(図は自動でループ再生されます)。

論文の図との対応 論文・プロジェクトページのアーキテクチャ図(main_model.png)は、 上の図と同じ構造を最小限の要素で描いています。すなわち 「Text Embed / Image Encoder🔒 / Audio Encoder🔒 が 1 本の入力列に交互に並び、 MLLM を経て、出力列の一部(連続特徴)が Decoder🔒 に入って画像になる」。 🔒 が付いているのはエンコーダとデコーダで、学習されるのは MLLM 側だけという 本解説の読み方と一致します。

なお論文の図では、Decoder に入る連続特徴が複数個(3 マス)描かれています。 学習コードも FEATURE_ID を複数並べられる作りですが、 公開されている generate_image() は先頭の 1 本だけを条件に使います (生成編の注記)。
公開コードの範囲について(重要) 本解説は microsoft/i-Code の CoDi-2 ディレクトリ(コミット 9b16730) を読んで書いています。このリリースはモデル定義と推論ロジックが中心で、学習ループ・データセット・チェックポイントは含まれていません。 実際、openllama.py の冒頭には from core.datasets.instruct_datasets.utils import FEATURE_ID という import がありますが、 core/datasets/ はリポジトリに存在しません。 そのため本解説では「損失計算・生成手続きのコードから読み取れる設計」を主役に据え、 そのままでは動かない箇所は都度⚠️で明示します。

CoDi-1 との違い — テキストの扱いが逆転した

同じ i-Code リポジトリには前作 CoDi(Composable Diffusion, NeurIPS 2023)のコードも同居していて、 CoDi-2 はその資産を再利用しています。しかしテキストの位置づけは正反対です。

CoDi-1 では、テキストもまた拡散で生成する 1 つのモダリティでした。 Optimus VAE が文を 768 次元の潜在ベクトルに畳み、それを専用 UNet(openai_unet_0dmd、 入出力チャンネル 768 の「0 次元」UNet)がデノイズする、という作りです。

CoDi-2/configs/model/openai_unet.yaml L55–84 GitHub ↗
openai_unet_0dmd:          # ← テキストを拡散生成するための UNet(CoDi-1)
  type: openai_unet_0dmd
  args:
    input_channels: 768    # Optimus VAE の文潜在の次元
    model_channels: 320
    output_channels: 768
    ...

openai_unet_codi:
  type: openai_unet_codi
  args:
    unet_image_cfg: MODEL(openai_unet_2d)
    unet_text_cfg: MODEL(openai_unet_0dmd)     # 画像・テキスト・音声の
    unet_audio_cfg: MODEL(openai_unet_2d_audio) # UNet が横並びで存在する
    model_type: ['video', 'image', 'text', 'audio']

CoDi-2 はここでテキストを LLM に返上します。LLM は元々テキストの専門家なのだから、 文章は自己回帰で書かせ、拡散モデルはテキスト以外の生成にだけ使う。 その代わり LLM には「拡散モデルが理解できる条件ベクトルを書く」という新しい仕事が課されます。

NExT-GPT との比較 — 同じ「接着」でも中身が違う

本シリーズのNExT-GPT 編と読み比べると、 「凍結した巨大モデルを小さな射影層で接着する」という骨格は共通なのに、 LLM から拡散モデルへ何を渡すかが根本的に違うことが見えてきます。

NExT-GPTCoDi-2
生成の合図 語彙に追加したシグナルトークン <image_00>…(埋め込み行を新規学習) 既存語彙で書けるただの文字列 <p>(語彙の拡張なし)
拡散モデルへ渡すもの 77×1024 のCLIP テキスト埋め込み列(prompt_embeds) 1×1024 のImageBind 画像埋め込み(c_adm)
拡散モデル側の条件づけ cross-attention(テキスト条件) unCLIP の adm 経路(クラス埋め込み相当)+ ノイズ拡張
整合の教師 凍結テキストエンコーダの出力 \(E_{\text{text}}(c)\) に L2 で寄せる ImageBind が返した実物の特徴に cosine で寄せる
拡散損失 常時併用(Min-SNR 重み付き) perception_type が clip-diffusser-back-proop のときだけ追加
入力エンコーダ ImageBind(1 モダリティ = 1 ベクトル) ImageBind(画像はパッチ列を返すよう改造)
学習の段階 3 ステージ(enc → dec → 指示チューニング) 公開コード上は単一の forward に全損失が同居(段階分けはフラグ次第)
ひとことで言うと NExT-GPT は LLM に「拡散モデル用のプロンプトを書かせる」。 CoDi-2 は LLM に「画像そのものの埋め込みを書かせる」。 前者は言語の比喩を最後まで維持し、後者は途中で言語を降りて連続空間に移る、という違いです。

学習と生成の見どころ(ダイジェスト)

学習: 損失は「トークンの当てっこ」+「ベクトルの向き合わせ」

forward が返すのは (loss, gen_acc, feature_loss) の 3 つ組で、 損失は次の 3 本です。

  1. テキスト CE 損失 \(=\mathcal{L}_t\): 標準の次トークン予測。ただし特徴を出すべき位置は -100 でマスクされ、CE の対象外
  2. 特徴回帰損失 \(=\alpha\,\mathrm{MSE}\): その位置の隠れ状態を codi_llama_decode に通し、 ターゲットの ImageBind 特徴に近づける(係数 0.1 = \(\alpha\)。 ただし論文は MSE、コードの主経路はコサイン類似度という差があります)
  3. 拡散損失 \(=\mathcal{L}_{DM}\): 生成した特徴で実際に拡散モデルを走らせ、そのノイズ予測誤差も足す (コード上は perception_type フラグで切り替わる)

また学習はテキスト・画像・音声の生成フェーズを交互に切り替えて進められます(論文 §B.2)。 コードの forward が if 'image' in inputs / elif 'text' / elif 'audio' と 1 バッチ 1 モダリティで書かれているのは、この方針の反映です。 数式とコードの対応は学習編で追いかけます。

生成: <p> という 3 トークンが分岐器

推論時、LLM の出力に <p>(LLaMA トークナイザで [529, 29886, 29958])が現れると、 その直後の位置の最終層隠れ状態が抜き出されます。 語彙に射影される前の生のベクトルなので、情報は連続のまま保たれます。 これを 1024 次元へ落とし、SD 2.1 unCLIP の c_adm に流し込めば画像が出てきます。詳細は生成編へ。

この設計が狙うタスク

なぜ「語彙を通さない連続特徴」にこだわるのか —— その答えは、 著者が挙げるタスク類型を見ると腑に落ちます。

類型内容
Zero-shot prompting 例示なしで推論し、新しい内容を生成する
Exemplar learning
(one/few-shot)		 「望ましい出力の例」を 1 つ見せてから、新しい入力に同じ操作を適用させる
Concept learning
(one/few-shot)		 複数の例に共通する概念・属性(画風やパターンなど)を学び取り、それを備えた新しい内容を作る
Subject-driven learning
(one/few-shot)		 与えられた画像群の被写体を保ったまま、新しい内容を生成する

いずれも「言葉にしきれないもの(画風・被写体の同一性・音色)を、例から拾って再現する」タスクです。 LLM の出力をいったんテキストに落としてから拡散モデルに渡す方式では、 この「言葉にならない情報」がボトルネックで削られてしまいます。 CoDi-2 が語彙を通さず ImageBind 空間のベクトルを直接手渡すのは、 まさにこの削れを避けるためだと読めます。 (タスク類型の出典: codi-2.github.io の “Tasks” 節)
