1. アーキテクチャ詳解

CoDi-2 の本体は openllama.py の OpenLLAMAPEFTModel クラス 1 つ。 改造 ImageBind・対称な 2 つの MLP・LoRA・ImageBind 条件の unCLIP を、テンソル形状を追って読み解きます。

形の全体像

まず、1024 と 4096 という 2 つの数字がどこで行き来しているかを掴んでください。 CoDi-2 のアーキテクチャは、突き詰めると 「ImageBind の 1024 次元」と「LLM の 4096 次元」の間を往復するだけです。

① 改造 ImageBind — 画像だけ「パッチ列」で返る

CoDi-2 は ImageBind をリポジトリ内にベンダリングしていますが、 本家からひとつ重要な変更が加えられています。 画像(VISION)ヘッドの SelectElement(index=0) がコメントアウトされているのです。

CoDi-2/core/models/mmllama/ImageBind/imagebind/models/imagebind_model.py L378–397 GitHub ↗
modality_heads[ModalityType.VISION] = nn.Sequential(
    nn.LayerNorm(normalized_shape=vision_embed_dim, eps=1e-6),
    nn.Identity(),
    # SelectElement(index=0),          # ← 本家ではここで CLS トークンだけを取り出していた
    nn.Linear(vision_embed_dim, out_embed_dim, bias=False),
)

modality_heads[ModalityType.TEXT] = SelectEOSAndProject(...)   # テキストは EOS 位置 1 本のまま

modality_heads[ModalityType.AUDIO] = nn.Sequential(
    nn.LayerNorm(normalized_shape=audio_embed_dim, eps=1e-6),
    nn.Identity(),
    SelectElement(index=0),            # ← 音声はコメントアウトされていない = 1 本のまま
    nn.Linear(audio_embed_dim, out_embed_dim, bias=False),
)

SelectElement は x[:, index, ...] を返すだけの層なので、 これを外すと画像ヘッドの出力は (B, 1024) ではなく (B, L, 1024)(L = CLS + パッチ数)になります。 つまり画像だけが「1 枚 = 複数トークン」として LLM に入る、というのが CoDi-2 の入力設計です。

なぜ画像だけ細かく入れるのか CoDi-2 が狙うのは「この画像のこの部分を、あの音のように編集して」といった 細かい指示追従です。1 枚を 1 ベクトルに潰してしまうと空間情報が失われるため、 入力側では意図的にパッチ列を保っています。一方出力側は 1 本のベクトルで十分 —— 拡散モデル(unCLIP)が要求する条件がまさに 1 本だからです。 この非対称性が CoDi-2 の設計の妙です。

この改造に呼応して、forward のエンコード部にも独特の正規化が現れます。

CoDi-2/core/models/mmllama/openllama.py L289–320(抜粋) GitHub ↗
if 'image' in inputs:
    self.perception_len = self.perception_len_image      # 画像は 1 枚 = perception_len トークン
    encoder_embeds_all = []
    for image_list in inputs['image']:
        if 'clip' in self.perception_type:
            with torch.no_grad():                        # ← ImageBind は常に凍結
                encoder_embeds_unnormed = self.imagebind({ModalityType.VISION:
                    data.load_and_transform_vision_data(image_list, self.device)})['vision']
                # CLS 位置のノルムで系列全体を割る = CLS を単位ベクトル化するスケーリング
                encoder_embeds = encoder_embeds_unnormed / torch.norm(
                    encoder_embeds_unnormed[:, :1], dim=-1, keepdim=True)
        encoder_embeds_all.append(encoder_embeds)
elif 'text' in inputs:
    self.perception_len = 1                              # テキストと音声は 1 サンプル = 1 トークン
    ...
elif 'audio' in inputs:
    self.perception_len = 1
    ...

画像だけ perception_len が可変で、テキストと音声は 1 に固定されている点に注目してください。 これは前述のヘッド改造と正確に対応しています。

② 2 つの MLP — 対称に置かれた「翻訳器」

CoDi-2 で新規に学習される重みは、LoRA を除けばこの 2 つの nn.Sequential がすべてです。

CoDi-2/core/models/mmllama/openllama.py L171–189 GitHub ↗
if 'clip' in self.perception_type:
    dim_in = 1024                                  # ImageBind の出力次元
    self.dim_in = dim_in
    dropout = 0.1
    dim_out = self.llama_model.config.hidden_size  # LLaMA-7B なら 4096

    self.codi_llama_proj = nn.Sequential(          # 入力用: 1024 → 4096
        nn.Linear(dim_in, dim_out),
        nn.GELU(),
        nn.LayerNorm(dim_out),
        nn.Linear(dim_out, dim_out),
    )

    self.codi_llama_decode = nn.Sequential(        # 出力用: 4096 → 1024
        nn.Linear(dim_out, dim_in),
        nn.GELU(),
        nn.LayerNorm(dim_in),
        nn.Linear(dim_in, dim_in),
    )
式で書くと $$P_{\text{in}}(\mathbf{v}) = W_2\,\mathrm{LN}\!\big(\sigma(W_1 \mathbf{v})\big),\qquad P_{\text{out}}(\mathbf{h}) = W_4\,\mathrm{LN}\!\big(\sigma(W_3 \mathbf{h})\big)$$ \(\sigma\) は GELU。\(P_{\text{in}}: \mathbb{R}^{1024}\to\mathbb{R}^{4096}\)、 \(P_{\text{out}}: \mathbb{R}^{4096}\to\mathbb{R}^{1024}\) と、次元がちょうど逆になっています。 重みは共有されておらず、それぞれ独立に学習されます。
NExT-GPT の出力プロジェクタとの違い NExT-GPT の出力プロジェクタは (2n−1, 4096) の隠れ状態列を受け取り、 Transformer で (77, 1024) という系列を作る必要がありました (CLIP テキストエンコーダの出力を模倣するため)。 CoDi-2 の codi_llama_decode は位置ごとに独立な MLPで、系列も作りません。 渡す相手が「テキスト埋め込み列」ではなく「画像埋め込み 1 本」だからこそ、ここまで単純化できています。

③ LLM と LoRA

LLM は HuggingFace の LlamaForCausalLM をそのまま読み込み、 PEFT の LoRA を注意機構の 4 つの射影に挿します。CoDi-2 は 語彙を 1 つも増やしません —— ここも NExT-GPT との大きな違いです。

重みは Vicuna ではなく Llama-2-7b-chat-hf コードの引数名は vicuna_ckpt_path ですが、論文 §5.1 は “Our implementation is based on Llama2, specifically Llama-2-7b-chat-hf” と明記しています。 引数名は PandaGPT / NExT-GPT 系の実装から受け継いだ名残と読むのが自然で、 実際に読み込まれるのは Llama-2-7B-chat です。 LoRA の rank も論文が 128 と指定しています(コードでは args['lora_r'] で外から与える形)。
CoDi-2/core/models/mmllama/openllama.py L149–165 GitHub ↗
# add the lora module
peft_config = LoraConfig(
    task_type=TaskType.CAUSAL_LM,
    inference_mode=False,
    r=self.args['lora_r'],
    lora_alpha=self.args['lora_alpha'],
    lora_dropout=self.args['lora_dropout'],
    target_modules=['q_proj', 'k_proj', 'v_proj', 'o_proj']   # 注意機構だけに LoRA
)

self.llama_model = LlamaForCausalLM.from_pretrained(
    vicuna_ckpt_path, cache_dir=args['data_dir'],
    torch_dtype=torch.float16, use_flash_attention_2=True)
self.llama_model = get_peft_model(self.llama_model, peft_config)
self.llama_model.print_trainable_parameters()

self.llama_tokenizer = LlamaTokenizer.from_pretrained(vicuna_ckpt_path, use_fast=False, ...)

語彙を増やさないので、embed_tokens も lm_head も一切触りません。 「モダリティを出せ」という合図は、既存語彙で書ける <p> という文字列と、 入力列に差し込まれる連続ベクトルだけで表現されます。

学習対象は 3 種類だけ —— 論文も同じことを言っている “The fine-tuning process focuses only on the LoRa weights and the projection layers that map modality encoders into the LLM input space, as well as the decoder layer that projects LLM-generated features into the diffusion input space.”(論文 §B.2)

これは codi_llama_proj / LoRA / codi_llama_decode の 3 つに正確に対応します。 ImageBind も拡散モデルも一切更新されません。

④ 入力列の組み立て — プレースホルダを実特徴で上書きする

LLM に渡す inputs_embeds は、 トークン ID の列をいったん普通に埋め込んでから、特定の位置だけ差し替えるという方法で作られます。 差し替え対象の目印が FEATURE_ID という特殊なトークン ID です。

論文が示すプロンプト形式(§3.1) 論文は、特徴列の前後をモダリティ名のタグで挟むと説明しています。 たとえば

“A cat sitting on [image0] is making the sound of [audio0]”
という modality-interleaved な入力は

“A cat sitting on <image> [image feature sequence] </image> is making the sound of <audio> [audio feature sequence] </audio>”

に変換されてから MLLM に入ります。 公開コードの PROMPT_START = '<Perception>' / '</Perception> '(学習編)と FEATURE_ID のプレースホルダは、この「タグ + 特徴列」構造を実装したものです。 タグはただの文字列で、特徴列の実体は下図のように埋め込みレベルで差し込まれます。
CoDi-2/core/models/mmllama/openllama.py L199–221(抜粋) GitHub ↗
encoder_embeds_all = []
for encoder_embeds in encoder_embeds_raw:
    if encoder_embeds is not None:
        embeds = self.codi_llama_proj(encoder_embeds)   # 1024 → 4096
        if embeds.ndim == 3:
            embeds = embeds.flatten(0, 1)               # (N, L, 4096) → (N*L, 4096) と平坦化
        encoder_embeds_all.append(embeds)
    else:
        encoder_embeds_all.append(None)

perception_indices = input_ids == FEATURE_ID            # ★ 差し込み位置のブールマスク
llm_embeds = self.llama_model.model.model.embed_tokens(input_ids)
input_embeds = torch.empty(llm_embeds.shape).to(llm_embeds)
input_embeds[~perception_indices] = llm_embeds[~perception_indices]   # テキスト側はそのまま

tmp_encoder_embeds_all = [item for item in encoder_embeds_all if item != None]
if len(tmp_encoder_embeds_all) > 0:
    concated_embeds = torch.cat(tmp_encoder_embeds_all, 0)
    if input_embeds[perception_indices].shape == concated_embeds[:input_embeds[perception_indices].shape[0]].shape:
        input_embeds[perception_indices] = concated_embeds[:input_embeds[perception_indices].shape[0]]  # ★ 上書き
形が合わなければ「黙って捨てる」実装 最後の if は、プレースホルダの個数と特徴の個数が食い違ったときに 例外を投げずに print して素通りする作りになっています(else 節)。 その場合 input_embeds の該当位置は torch.empty の未初期化値のままです。 研究コードらしい割り切りで、データ側で個数を正確に揃えることが前提になっています。

⑤ 画像生成器 — SD 2.1 unCLIP を ImageBind 条件に差し替えたもの

CoDi-2 の生成品質を支えているのは、この YAML 1 枚です。 ベースは Stable Diffusion 2.1 の unCLIP(画像バリエーション)版ですが、 条件を作る embedder_config が CLIP ではなく ImageBind に差し替えられています。

CoDi-2/configs/stable-diffusion/v2-1-stable-unclip-h-bind-inference.yaml L1–54(抜粋) GitHub ↗
model:
  target: ldm.models.diffusion.ddpm.ImageEmbeddingConditionedLatentDiffusion
  params:
    embedding_dropout: 0.25
    parameterization: "v"            # v-prediction
    conditioning_key: crossattn-adm  # ★ cross-attention と adm の 2 経路を併用
    image_size: 96                   # 768px ÷ 8 = 96
    channels: 4

    embedder_config:
      target: image_bind.models.imagebind_model.ImageBindEmbedder   # ★ CLIP ではなく ImageBind

    noise_aug_config:
      target: ldm.modules.encoders.modules.CLIPEmbeddingNoiseAugmentation
      params:
        timestep_dim: 1024           # ノイズレベル埋め込みも 1024 次元

    unet_config:
      params:
        num_classes: "sequential"
        adm_in_channels: 2048        # ★ 1024(特徴)+ 1024(ノイズレベル)= 2048
        context_dim: 1024            # cross-attention 側は OpenCLIP テキスト
2048 = 1024 + 1024 という足し算がすべてを説明する adm_in_channels: 2048 は、c_adm(ImageBind 特徴 1024 次元)と noise_level_emb(ノイズレベル埋め込み 1024 次元)を連結した長さです。 生成編で見るように、実装では c_adm_noise = torch.cat((c_adm, noise_level_emb), 1) と素直に連結されます。 LLM が 1024 次元を 1 本書けば、この UNet はそのまま動く —— CoDi-2 が「連続特徴空間で生成する」と言えるのは、この受け皿が用意されているからです。

なお conditioning_key: crossattn-adm のとおり、cross-attention 経路も生きています。 ただし生成編で見るように、実装ではこちらにネガティブプロンプトを固定で流すだけで、 意味的な制御はすべて c_adm 側が担います。

⑥ 画像以外のデコーダ

論文 §5.1 は、生成器として次の 3 つを挙げています。

モダリティ論文が指定する生成器条件の受け取り方
🖼️ 画像Stable Diffusion 2.1(stabilityai/stable-diffusion-2-1-unclip)c_adm(画像埋め込み条件)
🔊 音声AudioLDM2条件埋め込み
🎬 動画zeroscope v2 576w条件埋め込み

つまり CoDi-2 は、前作 CoDi(-1)の統合拡散モデルを丸ごと引き継いだのではなく、 モダリティごとに既製の拡散モデルを並べる構成に変わっています。 一方で公開コードには CoDi-1 由来の decode() が残っており、 潜在 z を各モダリティの VAE で戻す経路が書かれています。

CoDi-2/core/models/mmllama/openllama.py L529–570(抜粋) GitHub ↗
def decode(self, z, xtype):
    net = self.codi                                  # ← CoDi-1 モデル
    z = z.to(self.device)
    if xtype == 'image':
        x = net.autokl_decode(z)                     # Stable Diffusion の VAE
        x = torch.clamp((x+1.0)/2.0, min=0.0, max=1.0)
        x = [tvtrans.ToPILImage()(xi) for xi in x]
        return x
    elif xtype == 'video':
        num_frames = z.shape[2]
        z = rearrange(z, 'b c f h w -> (b f) c h w') # フレームを畳んで画像 VAE に通す
        x = net.autokl_decode(z)
        ...
    elif xtype == 'text':
        x = net.optimus_decode(z, temperature=1.0)   # Optimus VAE で潜在 → 文
        ...
    elif xtype == 'audio':
        x = net.audioldm_decode(z)                   # AudioLDM VAE
        x = net.mel_spectrogram_to_waveform(x)       # メルスペクトログラム → 波形
        return x
⚠️ 公開コードでは self.codi が組み立てられていない decode() や extract_multimodal_feature() は self.codi を参照しますが、 公開されている OpenLLAMAPEFTModel.__init__(L108–189)で実際に生成されるのは self.imagebind と self.image_diffuser の 2 つだけで、 self.codi はどこにも代入されていません。 同様に inference()(L572)が呼ぶ self.get_llm_outputs も定義されていません。 そのまま動くのは画像生成の経路(generate → generate_image)だけで、 音声(AudioLDM2)・動画(zeroscope v2)の経路は公開コードには含まれていません。

高忠実度が要るときの追加テクニック

論文 §5.1 には、生成条件をもう一段強める工夫が書かれています。

論文 §5.1 “For images or audio that require higher fidelity to the original input, we additionally feed the original image or audio to the diffusion model alongside the generated features by concatenation of the diffusion noise. This approach is particularly effective in preserving the most perceptual features of the input including instruction editing like adding new content or changing style.”

つまり「元画像を保ったまま編集する」タスクでは、 LLM が生成した特徴だけでなく元データの潜在をノイズにチャンネル方向で連結して UNet に入れる、というわけです。 この仕組みは CoDi-1 側のコードに x_0_att_type='concat' として実装されており、 codi.py の p_losses に x_noisy[i] = torch.cat([x_0[i], x_noisy[i]], 2) という形で現れます (codi.py L206–221)。
