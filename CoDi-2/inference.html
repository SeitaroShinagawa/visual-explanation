3. 生成プロセス

「この写真の犬を、さっきの絵のスタイルで描いて」と頼まれた CoDi-2 の中で何が起きるのか。 テキストと非テキストで出口が分かれる瞬間を、 generate() の実装から拡散サンプリングまで追跡します。

生成の全体タイムライン

CoDi-2 の推論は大きく 6 段階です。鍵になるのは 「LLM は最後まで普通に自己回帰生成しているだけ」という点で、 モダリティの切り替えは生成が終わったあとの後処理として実装されています。

入口 — プロンプトに特徴を織り込む

推論時のプロンプトは、#image#_0 のようなタグ付きの単語を含む 1 本の文字列として渡されます。process_and_concat_embeds がこれを 空白で分割し、タグなら射影済みの特徴を、そうでなければ通常のトークン埋め込みを並べていきます。

CoDi-2/core/models/mmllama/openllama.py L455–474 GitHub ↗
def process_and_concat_embeds(self, prompt, feature_embeds):
    batch_size = len(prompt)
    context_embeds = []
    for text in prompt[0].split(' '):                      # ★ 空白で切って 1 語ずつ処理
        if any(tag in text for tag in ['#image#', '#audio#', '#video#', '#text#']):
            modality_tag, index = text.split('_')          # 例: "#image#_0"
            projected_embed = self.codi_llama_proj(feature_embeds[modality_tag][int(index)].unsqueeze(0))
            context_embeds.append(projected_embed)         # 特徴を差し込む
        else:
            tokens = self.llama_tokenizer(text, return_tensors="pt", add_special_tokens=False).to(self.device)
            embeds = self.llama_model.model.model.embed_tokens(tokens.input_ids)
            context_embeds.append(embeds)                  # 普通のトークン埋め込み

    bos = torch.ones([batch_size, 1],
                     dtype=tokens.input_ids.dtype,
                     device=tokens.input_ids.device) * self.llama_tokenizer.bos_token_id
    bos_embeds = self.llama_model.model.model.embed_tokens(bos)
    inputs_embeds = torch.cat([bos_embeds] + context_embeds, dim=1)
    return inputs_embeds
学習時と推論時で入口の実装が違う 学習時は FEATURE_ID というトークン ID をマスクにして一括で上書きしていました (アーキテクチャ編 ④)。 推論時は文字列タグを逐次連結します。 結果として得られる inputs_embeds は同じ形ですが、 経路が二重化しているのは研究コードらしいところです。

テキストの生成 — 何も特別なことをしていない

generate() は HuggingFace の generate をそのまま呼びます。 サンプリング設定も普通で、CoDi-2 に固有なのは output_hidden_states=True と return_dict_in_generate=True —— つまり「あとで隠れ状態を使うから取っておいて」という指定だけです。

CoDi-2/core/models/mmllama/openllama.py L492–509 GitHub ↗
input_embeds = self.prepare_generation_embedding(inputs)
stopping_criteria = StoppingCriteriaList([StoppingCriteriaSub(stops=[2277], encounters=1)])
outputs = self.llama_model.generate(
    inputs_embeds=input_embeds,
    max_new_tokens=inputs['max_tgt_len'],
    top_p=inputs['top_p'],
    temperature=inputs['temperature'],
    do_sample=True,
    use_cache=True,
    stopping_criteria=stopping_criteria,
    return_dict_in_generate=True,
    output_hidden_states=True,        # ★ 非テキスト生成のために隠れ状態を保存
)
output_ids = outputs.sequences[0][1:]
output_text = self.llama_tokenizer.decode(output_ids, skip_special_tokens=True)
hidden_states_last = []
for item in outputs.hidden_states:
    hidden_states_last.append(item[-1].squeeze())         # 各ステップの「最終層」だけを集める

テキスト出力はここで完成です。 output_text は普通にデコードされた文字列で、 NExT-GPT のようにシグナルトークンを取り除く後処理すら要りません —— <p> は人間が読んでも違和感のないただのタグだからです。

非テキストの生成 — <p> という 3 トークン

続いて、生成された列から <p> を探します。

CoDi-2/core/models/mmllama/openllama.py L511–527 GitHub ↗
def find_pattern(sequence1, sequence2, pattern):
    results = []
    pattern_length = len(pattern)
    for i in range(len(sequence1) - pattern_length + 1):
        if sequence1[i:i+pattern_length].detach().cpu().tolist() == pattern:
            j = i + pattern_length - 1          # パターンの最後の位置
            if j + 1 < len(sequence2):
                results.append(sequence2[j + 1])  # ★ その「1 つ後ろ」の隠れ状態を採用
    return results

hidden_states_filtered = find_pattern(output_ids, hidden_states_last, [529, 29886, 29958])
if hidden_states_filtered:
    hidden_states_filtered = torch.stack(hidden_states_filtered)
    output_features = self.codi_llama_decode(hidden_states_filtered)   # (N, 4096) → (N, 1024)
else:
    output_features = None
return output_text, output_features
[529, 29886, 29958] は何か — 実際に引いてみた LLaMA の SentencePiece トークナイザで ID を引くと次のとおりです。
IDピース意味
529▁<空白付きの <
29886p文字 p
29958>文字 >
2277##停止条件に使われるトークン
実際 sp.encode('<p>') はちょうど [529, 29886, 29958] を返します。 つまり探しているのは「 <p> という 3 トークンの並び」で、 新しい語彙ではなく既存の文字を組み合わせただけのマーカーです。
1 つずらす理由 find_pattern が採るのは sequence2[j+1]、 つまり > を出力し終えた位置の隠れ状態です。 自己回帰モデルにおいて位置 \(t\) の隠れ状態は「\(t{+}1\) 番目に来るもの」を決めるので、 これは「<p> の次に来るべきもの」= 生成すべき特徴にほかなりません。 学習編②の hidden_states[-1][:, :-1] と regression_targets[:, 1:] の shift と、 きれいに同じ関係になっています。 なお output_ids = outputs.sequences[0][1:] の [1:] は、 inputs_embeds から生成したときに sequences の先頭に付く分を落として hidden_states 側と添字を合わせるためのものです。

核心 — テキストと非テキストの生成方法を並べる

ここまでを 1 枚の表に整理します。CoDi-2 の「any-to-any 生成」は、 この 2 列の非対称性で説明できます。

📝 テキスト🖼️🔊🎬 テキスト以外
出力の実体語彙 ID の列(離散)1024 次元ベクトル(連続)
通る層lm_head(4096 → 32000)codi_llama_decode(4096 → 1024)
確率的かYes(do_sample=True, top-p, temperature)No(決定的な線形変換)
生成のタイミング自己回帰ループの各ステップループ終了後にまとめて抽出
合図—直前に <p> が書かれていること
学習時の損失交差エントロピー負のコサイン類似度(+任意の拡散損失)
後段そのままユーザーへ拡散モデルの条件になり、デノイズを経て実データへ
「自己回帰的に連続特徴を生成する」の実際 論文・README は “autoregressively generate … in the continuous feature space” と述べており、 学習時は確かにその通り(1 つ前の隠れ状態から次の特徴を予測する)です。 一方公開されている推論コードでは、生成した特徴を入力列に戻して次のステップへ送る —— というフィードバックは行われていません。 generate() はテキストを最後まで生成し、そのあとで隠れ状態を後から拾います。 そのため <p> が複数回現れても、それぞれの特徴は 「そのときの隠れ状態」から独立に読み出される形になります。 複数特徴を真に連鎖させる推論を行うには、呼び出し側で多ターンに分けて回す必要があります。

拡散モデルの呼び出し — 条件は 1 本のベクトル

最後は generate_image() です。ここが CoDi-2 でいちばん面白い部分かもしれません。

CoDi-2/core/models/mmllama/openllama.py L577–604(抜粋) GitHub ↗
def generate_image(self, features, xtype, image_size=768, n_samples=1, ddim_steps=50, scale=7.5):
    from ldm.models.diffusion.ddim import DDIMSampler
    sampler = DDIMSampler(self.image_diffuser, device=self.device)

    c_adm = repeat(features, '1 ... -> b ...', b=n_samples)[:, 0]
    if self.image_diffuser.noise_augmentor is not None:
        c_adm, noise_level_emb = self.image_diffuser.noise_augmentor(c_adm, noise_level=(
                torch.ones(n_samples) * self.image_diffuser.noise_augmentor.max_noise_level * 0.5).long().to(c_adm.device))
        c_adm_noise = torch.cat((c_adm, noise_level_emb), 1)          # 1024 + 1024 = 2048

    uc_encoder = self.image_diffuser.get_learned_conditioning(
        n_samples * ['longbody, lowres, bad anatomy, bad hands, missing fingers, extra digit, '
                     'fewer digits, cropped, worst quality, low quality'])
    uc = {"c_crossattn": [uc_encoder], "c_adm": torch.zeros_like(c_adm_noise)}   # ★ 無条件側
    c = {"c_crossattn": [uc_encoder], "c_adm": c_adm_noise}                       # ★ 条件側

    samples, _ = sampler.sample(S=ddim_steps, conditioning=c, batch_size=n_samples,
                                shape=[4, image_size//8, image_size//8],
                                unconditional_guidance_scale=scale,       # 7.5
                                unconditional_conditioning=uc, eta=0.0, x_T=None)

    x_samples = self.image_diffuser.decode_first_stage(samples)
    x_samples = torch.clamp((x_samples + 1.0) / 2.0, min=0.0, max=1.0)

CFG が「画像埋め込みだけ」に効く仕掛け

c と uc をよく見比べてください。 c_crossattn(テキスト側)は完全に同じで、 違うのは c_adm が本物か zeros_like かだけです。 classifier-free guidance の差分 \(\epsilon_c - \epsilon_u\) はImageBind 特徴の寄与だけを取り出すことになります。

NExT-GPT との対比 NExT-GPT は prompt_embeds(77×1024 の CLIP テキスト埋め込み)を渡すので、 拡散モデルから見れば「長い文章でプロンプトされた」のと同じ状態でした。 CoDi-2 は c_adm(1×1024 の画像埋め込み)を渡すので、 拡散モデルから見れば「参照画像を 1 枚見せられた」のと同じ状態になります。 だからこそ CoDi-2 は「この被写体のまま別のポーズで」といった subject-driven な生成・編集に強い、という理屈になります。

画像以外のモダリティ

音声・動画については、CoDi-1 のデコーダを呼ぶ decode() が用意されています (アーキテクチャ編 ⑥)。 潜在 z を受け取って波形やフレーム列に戻すところまでは実装されていますが、 「1024 次元の特徴 → 潜在 z」を作る拡散サンプリングの配線は公開コードに含まれていません。

⚠️ 公開コードで実際に動く経路
  • 動く: テキスト生成(generate)、画像生成(generate_image)
  • 配線が足りない: 音声・動画生成。decode() と extract_multimodal_feature() が参照する self.codi が __init__ で生成されておらず、inference()(L572)が呼ぶ self.get_llm_outputs も未定義
  • 細かい点: generate_image の repeat(features, '1 ... -> b ...') は features の先頭次元が 1 であること、 すなわち (1, N, 1024) の形を前提にしていますが、 generate() が返すのは (N, 1024) です。 そのまま繋ぐと形が合わないため、呼び出し側で unsqueeze(0) 相当の調整が必要です
  • 特徴は何本使われるか: 続く [:, 0] が示すとおり、 generate_image が条件に使うのは先頭の 1 本だけです。 一方、論文・プロジェクトページの アーキテクチャ図では Decoder に入る連続特徴が複数マス描かれており、 学習側も FEATURE_ID を perception_len 個並べられる作りです。 公開された推論コードは、その一般形のうち最小構成だけを配線したものと読めます
公開されているのは研究コードのスナップショットであり、 配布されている推論スクリプトやチェックポイントとセットで動く前提のものと考えるのが妥当です。 本解説はこれらを「設計を読むための資料」として扱っています。

まとめ

CoDi-2 の生成プロセスを 3 行で
  1. LLM はふつうに文章を書く。その中に <p> という 3 トークンを書くことがある。
  2. <p> の直後の隠れ状態を codi_llama_decode に通すと、ImageBind 空間の 1024 次元ベクトルになる。
  3. そのベクトルを条件に、ImageBind 対応の unCLIP 拡散モデルを回すと画像が出る。語彙を通らないので情報が丸められない。

NExT-GPT が「LLM に拡散モデル用のプロンプトを書かせる」道を選んだのに対し、 CoDi-2 は「LLM に画像そのものの埋め込みを書かせる」道を選びました。 どちらも凍結モデルを小さな射影層で接着する点では同じですが、 やりとりする表現が「言語的なもの」か「知覚的なもの」かという違いが、 得意なタスク(指示追従の文脈理解 vs 被写体・スタイルの保存)の違いに直結しています。
